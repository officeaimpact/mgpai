## 🔴 ПРОБЛЕМА 1: МОДЕЛЬ ОПИСЫВАЕТ ДЕЙСТВИЕ ВМЕСТО ВЫПОЛНЕНИЯ (CRITICAL)

### Симптомы
Модель отвечает текстом типа:
> "Сейчас начну поиск подходящих туров для вас."

...но **НЕ вызывает** функцию `search_tours()`.

### Найденные случаи
- **dialogue_20260208_131433.md, строка 338:**
  ```
  [2026-02-08 13:15:01.342] 🤖 ASSISTANT
  Сейчас начну поиск подходящих туров для вас.
  ```
  Пользователь ждет несколько секунд, затем пишет:
  ```
  [2026-02-08 13:15:13.838] 👤 USER
  где туры?
  ```

### Последствия
- **UX:** Клиент не понимает, что происходит, теряет доверие к системе
- **Задержки:** Дополнительное время ожидания + лишнее сообщение от пользователя
- **API costs:** Лишний roundtrip к модели

### Корневая причина
Модель **игнорирует** критическое правило `system_prompt.md` раздел **0.0.1**:
```
⛔ АБСОЛЮТНЫЙ ЗАПРЕТ: НЕ описывай действие — ДЕЛАЙ его!

❌ Плохо: "Сейчас начну поиск подходящих туров для вас."
✅ Хорошо: <вызов search_tours()> + "Показываю результаты"
```

### Текущая попытка исправления
В `yandex_handler.py` (строки 52-79) реализован детектор `_is_promised_search()`:
```python
def _is_promised_search(text: str) -> bool:
    """Проверяет, обещала ли модель начать поиск, но не вызвала функцию."""
    triggers = [
        r"\bначн[уюеёа]\s+поиск",
        r"\bсейчас.*поиск",
        r"\bподберу.*тур",
        # ...
    ]
```

При детекции система добавляет nudge (строки 1103-1115):
```python
if _is_promised_search(final_text):
    logger.warning("🤖⚠️ Модель обещала поиск, но не вызвала функцию!")
    nudge = "⚠️ Ты обещал(а) начать поиск, но не вызвал(а) функцию search_tours."
    # ...повторный вызов модели
```

**Но это НЕ работает надежно**, так как модель может не среагировать на nudge или повторить ошибку.

## 🔴 ПРОБЛЕМА 2: НЕКОРРЕКТНЫЙ РАСЧЕТ `dateto` (CRITICAL)

### Симптомы
Функция `search_tours` вызывается с **некорректным** параметром `dateto`, например:
```json
{
  "datefrom": "04.04.2026",
  "dateto": "16.02.2026"  // ← дата В ПРОШЛОМ относительно datefrom!
}
```

### Найденные случаи
- **server_20260207_194103.log, строка 123:**
  ```
  [2026-02-07 19:41:15,469] DEBUG search_tours called with params={
    'datefrom': '04.04.2026', 
    'dateto': '16.02.2026', 
    'departure': 1, 
    'country': 1
  }
  ```
  Результат: `hotelsfound=0` (поиск вернул 0 отелей)

- **dialogue_20260207_194103.md, строка 66:**
  Функция вызвана, но пользователь не получил результатов.

### Последствия
- **UX:** Пользователь видит "нет результатов" при валидном запросе
- **API costs:** Лишние вызовы API TourVisor без результата
- **Репутация:** Клиент думает, что система не работает

### Корневая причина
**Конфликт двух слоев валидации:**

1. **В `tourvisor_client.py` (строки 285-293):**
   ```python
   # Если dateto не указан, установить datefrom как дефолт
   if not date_to:
       date_to = date_from  # ← ОПАСНО: может быть равно datefrom
       logger.warning("⚠️ dateto не указан, установлен = datefrom (%s)", date_to)
   ```

2. **В `yandex_handler.py` (строки 436-466):**
   ```python
   # Случай 1: dateto не указан → авто-установка datefrom + 2
   if not args.get("dateto"):
       args["dateto"] = (df + timedelta(days=2)).strftime("%d.%m.%Y")
       logger.warning("⚠️ dateto не указан, установлен = datefrom+2 (%s)", args["dateto"])
   
   # Случай 2: dateto == datefrom → расширить до datefrom+2
   if args["dateto"] == args["datefrom"]:
       args["dateto"] = (df + timedelta(days=2)).strftime("%d.%m.%Y")
       logger.warning("⚠️ dateto == datefrom, расширен до datefrom+2 (%s)", args["dateto"])
   
   # Случай 3: dateto < datefrom → clamp
   if dt < df:
       args["dateto"] = (df + timedelta(days=2)).strftime("%d.%m.%Y")
       logger.warning("⚠️ dateto < datefrom, исправлен на datefrom+2 (%s)", args["dateto"])
   ```

**Проблема:**
- Модель иногда передает `dateto` в неправильном формате или с ошибкой парсинга
- Коррекция в `yandex_handler.py` не срабатывает, если дата уже пришла некорректной из модели
- В логах видно, что `dateto=16.02.2026` при `datefrom=04.04.2026` — это указывает на ошибку самой модели

### Дополнительная причина
**System prompt неясен по поводу `dateto`:**

В `system_prompt.md` раздел 3.2 написано:
```
Если юзер говорит «5 марта на 7 дней» — это:
  datefrom = 05.03.2026
  dateto = 05.03.2026 + 2 дня = 07.03.2026
  nights = 7
```

Но модель интерпретирует как:
```
dateto = datefrom + 7 дней (дата возвращения)
```

Это **семантическая ошибка в понимании**.

## 🟠 ПРОБЛЕМА 3: ПРОПУСК КАСКАДА СБОРА ИНФОРМАЦИИ (HIGH)

### Симптомы
Функция `search_tours` вызывается **БЕЗ** полного набора обязательных параметров:
- `adults` (количество взрослых)
- `child` (количество детей)
- `stars` (звездность отеля)
- `meal` (тип питания)

### Найденные случаи
- **dialogue_20260207_183515.md, строка 48:**
  ```json
  {
    "country": 1,
    "datefrom": "14.02.2026",
    "dateto": "21.02.2026",
    "departure": 1
    // ← нет adults, child, stars, meal!
  }
  ```

  **Контекст диалога:**
  - Пользователь: "хотим с мужем в египет"
  - Пользователь: "москва"
  - Модель → вызов `get_current_date()`
  - Модель → **сразу** вызов `search_tours()` (ОШИБКА!)

  **Что пропущено:**
  - **Слот 4:** Состав путешественников (adults=2, child=0)
  - **Слот 5:** Quality check (stars, meal)

### Последствия
- **UX:** Пользователь не получает персонализированные результаты
- **API costs:** Поиск с дефолтными параметрами (обычно adults=2, stars=3, meal=1) может не соответствовать ожиданиям
- **Репутация:** Клиент видит неподходящие отели

### Корневая причина
Модель **игнорирует** обязательное правило `system_prompt.md` раздел **0.4**:
```
0.4 Порядок каскада (СТРОГИЙ)
Ты должен последовательно выяснить:
1) Direction (Направление)
2) DepartureTown (Город вылета)
3) Dates (Даты / длительность)
4) Composition (Состав путешественников)
5) Quality (Качество отеля / питания)

⛔ search_tours() — ЗАПРЕЩЁН до сбора ВСЕХ 5 слотов!
```

**Почему это происходит:**
- Модель может "догадаться" о параметрах из контекста ("с мужем" = 2 взрослых)
- Но **не спрашивает явно**, нарушая правило "СПРОСИ, даже если кажется, что знаешь"

- Не понимает, что frontend уже отобразит карточки визуально

## 🟡 ПРОБЛЕМА 6: НЕПРАВИЛЬНАЯ ИНТЕРПРЕТАЦИЯ "5 МАРТА НА 7 ДНЕЙ" (MEDIUM)

### Симптомы
Пользователь говорит: **"5 марта на 7 дней"**

Модель интерпретирует как:
```json
{
  "datefrom": "05.03.2026",
  "dateto": "12.03.2026",  // ← 05.03 + 7 дней
  "nights": 7
}
```

**Но правильно:**
```json
{
  "datefrom": "05.03.2026",
  "dateto": "07.03.2026",  // ← 05.03 + 2 дня (окно вылета)
  "nights": 7
}
```

### Корневая причина
**Семантическая путаница в system prompt:**

В `system_prompt.md` раздел 3.2 написано:
```
dateto — это НЕ дата возвращения, а ОКНО ВЫЛЕТА (±1–2 дня от datefrom)

Если юзер говорит «5 марта на 7 дней»:
  datefrom = 05.03.2026
  dateto = 05.03.2026 + 2 дня = 07.03.2026
  nights = 7
```

**Но это неинтуитивно:**
- Обычный человек думает: "5 марта на 7 дней" = вылет 5 марта, возвращение 12 марта
- Модель пытается следовать этой логике, но система требует другую

### Решение
**Вариант A:** Исправить логику в коде (упростить)
- Разрешить `dateto = datefrom + nights` (как ожидает пользователь)
- Скорректировать TourVisor API клиент

**Вариант B:** Улучшить промпт
- Добавить больше примеров
- Использовать другую терминологию (например, "окно поиска" вместо "dateto")
