### 1.2 Что МОЖНО безопасно сократить (30–40% — СРЕДНИЙ риск)

**B) Сократить секцию обработки ошибок (экономия ~50 строк, 0 риска):**

### 1.3 Что НЕЛЬЗЯ сокращать (критично для работы)

| Элемент | Почему критичен | Что произойдёт при удалении |
|---|---|---|
| **Правило `dateto = datefrom + 2`** | КОНТРИНТУИТИВНО. Модель по умолчанию считает dateto = datefrom + nights | Туры не найдутся или найдутся неправильные |
| **5 слотов каскада и их порядок** | Ядро бизнес-логики. Quality Check ВСЕГДА последний | Модель начнёт спрашивать о звёздах до дат, пропускать слоты |
| **Таблицы кодов (секция 6)** | Без кодов модель будет вызывать get_dictionaries на каждый запрос | Дополнительные API-вызовы, замедление, доп. расходы |
| **Правило «НЕ описывай — ДЕЛАЙ»** | Без него модель скажет «Сейчас поищу» вместо вызова функции | Потеря 1 API-вызова на каждый поиск |
| **Формат карточек (НЕ дублируй)** | Без него модель будет перечислять все отели текстом | UX-деградация, длинные ответы |
| **Правила конвертации дней→ночей** | API принимает ночи, клиенты говорят в днях | Неправильная длительность поиска |

### 1.4 Конкретная оценка рисков при сокращении на 30–40%

```
ПРОМПТ: 1532 строк → ~950 строк (~20 000 → ~13 000 токенов)

Экономия на input: ~7 000 токенов × 0,0012 ₽ = ~8,4 ₽ за вызов
При 10 вызовах/диалог: ~84 ₽/диалог (из 324 ₽ = 26% экономии)
```

| Риск | Вероятность | Последствие | Митигация |
|---|---|---|---|
| Модель забудет порядок каскада | НИЗКАЯ (правило остаётся) | Неправильный порядок вопросов | Оставить правило порядка, убрать только примеры |
| Ошибки в парсинге дат | СРЕДНЯЯ (убираем edge cases) | Неправильные dateto/nightsfrom | Бэкенд уже корректирует dateto (строки 517–563) |
| «Обещанные поиски» вернутся | НИЗКАЯ (правило остаётся 1 раз) | +1 холостой вызов изредка | `_is_promised_search()` уже ловит в бэкенде |
| Потеря тона/стиля | МИНИМАЛЬНАЯ | Чуть более формальные ответы | Приемлемо для бизнеса |

### 1.5 Почему сокращение на 60%+ ОПАСНО

При попытке сжать промпт до ~500 строк (~8 000 токенов) придётся резать:

1. **Примеры дат** — полностью. Без них модель БУДЕТ ошибаться в edge cases:
   - «с 8, 9 мая на 8-10 ночей» — модель не поймёт что 8,9 — это диапазон вылета
   - «вылет 17.08-21.08 на 11 ночей» — может посчитать это как 4 ночи
   - «в конце марта на неделю» — может не знать что «конце» = 20–31

2. **Таблицы кодов** — частично. Каждый удалённый код = доп. вызов `get_dictionaries` = +33 ₽

3. **Правило dateto** — может потерять контекст среди уплотнённых инструкций. Это САМАЯ ДОРОГАЯ ошибка, т.к. неправильный dateto = нерелевантные результаты.

**Вердикт:** Сокращение на 60%+ технически возможно, но требует **минимум 50–100 тестовых диалогов** для валидации. Без тестирования — ЗАПРЕЩЕНО.

## 2. YANDEX GPT LITE ДЛЯ СБОРА ДАННЫХ

### 2.1 Почему это предложение ОПАСНО

YandexGPT Lite — облегчённая модель с **значительно худшим следованием инструкциям**. Цена: 200 ₽/1M input (в 6 раз дешевле Pro).

Для понимания масштаба проблемы — вот что должна делать модель при сборе слота «даты»:

```
Ввод клиента: "с 8, 9 мая на 8-10 ночей"

Модель ДОЛЖНА:
1. Понять что "8, 9 мая" — это диапазон дат вылета (а не 89 мая)
2. Преобразовать: datefrom=08.05.2026, dateto=09.05.2026
3. Понять "8-10 ночей" как nightsfrom=8, nightsto=10
4. НЕ путать "ночей" с "дней" (8 дней = 7 ночей, но 8 ночей = 8 ночей)
5. НЕ считать dateto = datefrom + nights (контринтуитивное правило)
6. Запомнить это в контексте для будущего function call
```

YandexGPT Lite справляется с простыми задачами (классификация, извлечение сущностей), но **НЕ надёжна** при:
- Многошаговом следовании сложным инструкциям
- Удержании контринтуитивных правил (dateto ≠ дата возвращения)
- Конвертации форматов (дни→ночи, даты→API параметры)

### 2.2 Конкретные сценарии провала

| Ввод клиента | Что сделает Pro | Что вероятно сделает Lite |
|---|---|---|
| «23 марта на неделю» | `dateto=25.03` (правильно: +2 дня) | `dateto=30.03` (ошибка: +7 дней) |
| «на майские праздники» | `datefrom=28.04, dateto=11.05` | Может не знать точные даты |
| «до 10 дней» | `nightsfrom=3, nightsto=9` | Может поставить `nightsto=10` |
| «в конце марта» | `datefrom=20.03, dateto=31.03` | Может дать `datefrom=25.03, dateto=31.03` |
| «2 взр + ребёнок» | Спросит возраст ребёнка | Может забыть спросить возраст |

### 2.3 Дополнительные проблемы двухмодельной архитектуры

1. **Передача контекста:** Переключение между Lite и Pro требует передачи всего контекста. В Responses API с `previous_response_id` это невозможно — каждая модель имеет свою историю. Придётся пересылать `full_history`, что **удвоит** input-токены при переключении.

2. **Определение момента переключения:** Когда переключаться на Pro? Если после сбора 5 слотов — нужен детектор заполненности на бэкенде. Он уже есть (`_check_cascade_slots`), но работает по паттернам, не по семантике. Клиент может сказать «мне всё равно» (skip quality check) — и Lite должна это распознать.

3. **Fallback при ошибке Lite:** Если Lite неправильно распарсила даты, ошибка всплывёт только при получении результатов поиска (неправильные туры). Клиент увидит нерелевантные результаты и уйдёт.

### 2.4 Вердикт

```

║  Экономия: ~50% на этапе сбора (~100 ₽/диалог)              ║
║  Риск: Неправильные даты/состав → нерелевантные результаты   ║
```

## 3. УСТРАНЕНИЕ ХОЛОСТЫХ КАСКАДНЫХ ВЫЗОВОВ

### 3.1 Текущая проблема (из логов)

Когда модель вызывает `search_tours` с неполными данными, бэкенд:
1. Получает вызов (модель уже потратила ~33 ₽ на API-вызов)
2. Проверяет слоты через `_check_cascade_slots()`
3. Возвращает ошибку модели
4. Модель тратит ЕЩЁ ~33 ₽ на генерацию вопроса

**Итого:** 2 API-вызова × 33 ₽ = ~66 ₽ на каждый пропущенный слот, вместо 1 × 33 ₽ = 33 ₽.

### 3.2 Предлагаемое решение (БЕЗОПАСНО)

**Вариант A: Ответ без модели (максимальная экономия)**

Вместо возврата ошибки модели — бэкенд сам генерирует вопрос:

```python
# Текущее поведение (стоит 2 вызова):
if not is_cascade_complete:
    return {"error": "Спроси клиента..."}  # Модель тратит ещё 1 вызов чтобы сказать это

# Новое поведение (стоит 0 вызовов):
if not is_cascade_complete:
    # Не отправляем в модель вообще! Возвращаем ответ напрямую
    question = NUDGE_QUESTIONS[missing_slots[0]]
    return DirectResponse(text=question)  # Отправляем клиенту без вызова модели
```

**Шаблоны ответов для прямой отправки:**
| Пропущенный слот | Ответ (шаблон) |
|---|---|
| Город вылета | «Из какого города планируете вылет?» |
| Даты | «Когда планируете поездку и на сколько ночей?» |
| Состав | «Сколько взрослых едет и будут ли с вами дети?» |
| Quality Check | «Какую категорию отеля и тип питания предпочитаете?» |

### 3.3 Оценка рисков

| Риск | Вероятность | Реальность |
|---|---|---|
| Потеря естественности ответов | НИЗКАЯ | Сравните с текущими ответами модели — они ИДЕНТИЧНЫ шаблонам! |
| Потеря контекста | НУЛЕВАЯ | Проверка делается ДО вызова модели. Контекст не затрагивается |
| Неправильный вопрос | НУЛЕВАЯ | Вопросы зашиты в коде, не генерируются |
| Модель «забудет» что спрашивала | НИЗКАЯ | `full_history` сохраняет все сообщения, включая шаблонные |

**Доказательство из логов — ответы модели УЖЕ шаблонные:**

```
Модель сказала: "Из какого города планируете вылет?"              ← ИДЕНТИЧНО шаблону
Модель сказала: "Сколько взрослых едет и будут ли с вами дети?"   ← ИДЕНТИЧНО шаблону
Модель сказала: "Какую категорию отеля и тип питания предпочитаете?" ← ИДЕНТИЧНО шаблону
```

Модель каждый раз тратит ~33 ₽ чтобы сгенерировать **ту же самую фразу**, которую можно отдать бесплатно.

### 3.4 Реализация

**Вариант A (сильный — без модели):**

Перехватывать на уровне `chat()` ПЕРЕД отправкой в API. Если `_check_cascade_slots` говорит что слоты неполные — сразу вернуть шаблонный ответ.

- Экономия: **2 API-вызова** на каждый пропущенный слот = **~66 ₽/случай**
- Риск: Минимальный
- Сложность реализации: **Низкая** (20–30 строк кода)

**Вариант B (мягкий — 1 вызов вместо 2):**

Добавлять результат проверки каскада в input_list как системное сообщение ДО вызова API:

```python
if not is_cascade_complete:
    self.input_list.append({
        "role": "system", 
        "content": f"ПЕРЕД ответом: спроси клиента о {missing_slots[0]}. НЕ вызывай search_tours."
    })
    # Далее обычный API-вызов — модель прочтёт подсказку и сгенерирует вопрос
```

- Экономия: **1 API-вызов** на каждый пропущенный слот = **~33 ₽/случай**
- Риск: Ниже нуля (модель получает подсказку)
- Сложность: **Минимальная** (5–10 строк кода)

## 4. КЭШИРОВАНИЕ СПРАВОЧНИКОВ

### 4.1 Проблема

В сессии 2 модель вызвала `get_dictionaries(type=region, regcountry=4)` чтобы получить код Аланьи. Но код Аланьи (19) уже есть в системном промпте (секция 6.4). Модель «забыла» его и потратила 1 API-вызов (~33 ₽) на получение.

### 4.2 Решение

Перехватывать на бэкенде: если запрошен справочник стран/регионов для которого есть кэш — возвращать из кэша мгновенно, без вызова Tourvisor API.

Это уже работает для некоторых случаев, но можно расширить.

### 4.3 Вердикт

- Риск: **НУЛЕВОЙ** (справочники стран/регионов не меняются)
- Экономия: ~1 API-вызов на ~20% диалогов = ~7 ₽/диалог в среднем
- Сложность: **Низкая**

| Оптимизация | Механизм хранения контекста | Риск потери |
|---|---|---|
