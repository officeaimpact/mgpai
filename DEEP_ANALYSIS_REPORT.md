### Проблема 2: 🔴 Некорректная интерпретация `dateto`

**Местоположение:** `server_20260208_153000.log`, строки 48, 131

**Проблемное поведение:**
```python
# Модель генерирует:
search_tours({
    "datefrom": "08.02.2026",
    "dateto": "15.02.2026",  # ❌ datefrom + 7 ночей = 15.02
    "nightsfrom": 7,
    "nightsto": 7
})

# Код yandex_handler.py ИСПРАВЛЯЕТ на лету:
INFO [mgp_bot] ⚠️ DATE-VALIDATION: dateto 15.02.2026 > datefrom 08.02.2026 + 2 days → clamping to 10.02.2026
```

**Нарушенное правило:**
- `system_prompt.md` § 3.2, таблица "Конкретная дата + длительность":
  > ⛔ **КРИТИЧЕСКОЕ ПРАВИЛО:** `dateto` — это **последняя допустимая дата ВЫЛЕТА**, а **НЕ** дата возвращения!  
  > При «конкретная дата + длительность»: **`dateto = datefrom + 2 дня`** (окно вылета ±2 дня).  
  > **НИКОГДА** не считай `dateto = datefrom + nights` — это ГРУБАЯ ОШИБКА!

**Примеры из системного промпта:**
```
Пользователь: "21 февраля на неделю"
✅ Правильно: datefrom=21.02.2026, dateto=23.02.2026, nightsfrom=7, nightsto=7
❌ Неправильно: dateto=28.02.2026 (это дата возвращения!)
```

**Анализ корневой причины:**

Yandex GPT модель семантически путает `dateto` из-за контринтуитивного определения:
- **Естественное понимание:** "21 февраля на неделю" → вылет 21.02, возврат ~28.02
- **Требуемое API:** `dateto` = окно поиска вылетов (21.02-23.02), а длительность = `nightsfrom/nightsto`

Модель **упорно** интерпретирует `dateto` как "дату возвращения", несмотря на правило в промпте.

**Текущая защита в коде:**

`yandex_handler.py`, строки 448-465 (функция `_dispatch_function`):
```python
if "dateto" in args and "datefrom" in args:
    try:
        date_from = _dt.strptime(args["datefrom"], "%d.%m.%Y")
        date_to = _dt.strptime(args["dateto"], "%d.%m.%Y")
        delta = (date_to - date_from).days
        if delta > 2:
            # Принудительно сжимаем окно до 2 дней
            correct_dateto = (date_from + _td(days=2)).strftime("%d.%m.%Y")
            logger.warning("⚠️ DATE-VALIDATION: dateto %s > datefrom %s + 2 days → clamping to %s",
                           args["dateto"], args["datefrom"], correct_dateto)
            args["dateto"] = correct_dateto
    except ValueError:
        pass
```

**Эффективность защиты:**
- ✅ Код **успешно исправляет** ошибки модели на лету (видно в логах)
- ✅ API получает корректные параметры
- ⚠️ Модель продолжает **не понимать** правило (паллиатив, а не решение)

**Почему модель не понимает:**

1. **Семантическая контринтуитивность:** `dateto` в обычной речи ассоциируется с концом периода, а не с окном поиска
2. **Конфликт с названием параметра:** `dateto` звучит как "дата до" (конечная дата), а не "последняя дата поиска вылетов"
3. **Длинный промпт:** Правило в § 3.2 может теряться в 1485 строках промпта
4. **Недостаточное подкрепление:** Правило есть в таблице, но нет в разделе 0 (критические правила)

**Предложенные решения:**

**Вариант A (минимальный):** Усилить правило в промпте
- Переместить правило `dateto = datefrom + 2` в секцию § 0 (наивысший приоритет)
- Добавить примеры в начало промпта
- Добавить эмодзи и визуальное выделение
- **Плюсы:** Быстро, не требует изменения кода
- **Минусы:** Не гарантирует понимание, паллиатив

**Вариант B (средний):** Дополнительная валидация + nudge
- Если модель генерирует `delta > 2`, делать `continue` с nudge-сообщением (как в `_is_promised_search`)
- Давать модели второй шанс исправиться
- **Плюсы:** Обучает модель через feedback loop
- **Минусы:** Увеличивает количество итераций, возможны зацикливания

**Вариант C (идеальный):** Автоисправление + мониторинг
- Оставить текущую защиту (clamping)
- Добавить метрику для отслеживания частоты исправлений
- Если > 50% запросов требуют исправления → обратиться к Yandex за fine-tuning модели
- **Плюсы:** Не ухудшает UX, даёт данные для долгосрочного решения
- **Минусы:** Не устраняет корневую причину, требует мониторинга

**Рекомендация:** Вариант C (автоисправление + мониторинг)
- Текущая защита работает эффективно
- Проблема не влияет на конечного пользователя (API получает корректные данные)
- Риск регрессии от изменений выше, чем польза от "обучения" модели

```python
def _check_cascade_complete(args: dict, full_history: list) -> tuple[bool, str]:
    """
    Проверяет, что все 5 слотов каскада явно собраны от пользователя.
    Возвращает (is_complete, missing_slot_name)
    """
    # Слот 3: Даты
    if "datefrom" not in args or "nightsfrom" not in args:
        # Проверяем, спрашивал ли ассистент о датах и ответил ли пользователь
        user_mentioned_dates = any(
            re.search(r'\d{1,2}\.\d{1,2}|\d{1,2}\s+\w+|марта|апреля|мая', msg["content"], re.I)
            for msg in full_history if msg["role"] == "user"
        )
        if not user_mentioned_dates:
            return False, "dates"
    
    # Слот 4: Состав
    if "adults" not in args:
        user_mentioned_travelers = any(
            re.search(r'взрослы[хй]|детей|ребенок|один|двое|трое|человек[а]?', msg["content"], re.I)
            for msg in full_history if msg["role"] == "user"
        )
        if not user_mentioned_travelers:
            return False, "travelers"
    
    # Слот 5: Quality Check (опционально, но должно быть явно пропущено)
    # Пропускаем, если клиент сказал "любой" / "не важно"
    
    return True, ""

# В _dispatch_function, перед вызовом search_tours:
if function_name == "search_tours":
    is_complete, missing = _check_cascade_complete(args, self.full_history)
    if not is_complete:
        logger.warning("⚠️ CASCADE-INCOMPLETE: missing slot '%s' — blocking search", missing)

            "error": f"СИСТЕМНАЯ ОШИБКА: Ты пытаешься вызвать search_tours, но НЕ собрал все обязательные слоты! "

        }
```

### Проблема 6: 🟠 Семантическая путаница дат

**Тип:** Дизайн API / Когнитивная нагрузка на модель

**Суть:** Параметр `dateto` в TourVisor API семантически контринтуитивен:
- Название подразумевает: "дата ДО которой искать" (конечная точка периода)
- Реальное значение: "последняя допустимая дата ВЫЛЕТА" (окно поиска)

**Пример путаницы:**
```
Пользователь: "5 марта на неделю"

- Вылет: 05.03.2026
- Длительность: 7 ночей
- Возврат: ~12.03.2026
- dateto = 12.03.2026 (логично звучит как "искать до 12 марта")

Требуемое API:
- datefrom = 05.03.2026
- dateto = 07.03.2026 (окно вылетов: 05-07 марта)
- nightsfrom/nightsto = 7 (длительность)
```

**Анализ:**

Это **проблема дизайна API**, а не ошибка модели или промпта. Для модели (и людей!) естественно ассоциировать:
- `date_from` → начало периода
- `date_to` → конец периода

Но API использует:
- `datefrom` / `dateto` → окно поиска ВЫЛЕТОВ
- `nightsfrom` / `nightsto` → длительность (отдельный параметр)

**Текущее состояние:**

1. ✅ Защита в коде работает (автоисправление `dateto`)
2. ✅ API получает корректные параметры
3. ⚠️ Модель продолжает "не понимать" (когнитивная нагрузка)
4. ⚠️ Промпт содержит правило, но оно контринтуитивно

**Долгосрочное решение:**

**Опция 1:** Переименовать параметры API (breaking change):
```python
# Вместо:
search_tours(datefrom, dateto, nightsfrom, nightsto)

# Использовать:
search_tours(
    departure_date_from,    # Начало окна вылетов
    departure_date_to,      # Конец окна вылетов
    nights_min,             # Мин. длительность
    nights_max              # Макс. длительность
)
```

**Опция 2:** Адаптер на уровне модели:
```python
# Модель генерирует интуитивные параметры:
{
    "departure_date": "05.03.2026",
    "nights": 7,
    "date_flexibility": "+/- 2 days"
}

# Адаптер преобразует в API TourVisor:
{
    "datefrom": "05.03.2026",
    "dateto": "07.03.2026",
    "nightsfrom": 7,
    "nightsto": 7
}
```

**Рекомендация:** Оставить как есть (автоисправление работает)
- Опции 1 и 2 требуют значительных изменений
- Риск регрессии высокий
- Текущая защита эффективна
- Проблема не влияет на конечного пользователя

```python
@app.route('/api/metrics', methods=['GET'])
def get_metrics():
    """Возвращает агрегированные метрики по всем активным сессиям"""
    with _handlers_lock:
        aggregated = {
            "total_sessions": len(_handlers),
            "promised_search_detections": 0,
            "cascade_incomplete_detections": 0,
            "dateto_corrections": 0,
            "redundant_dictionaries_calls": 0,
        }
        
        for session_data in _handlers.values():
            handler = session_data["handler"]
            metrics = handler.get_metrics()
            for key in ["promised_search_detections", "cascade_incomplete_detections", 
                        "dateto_corrections", "redundant_dictionaries_calls"]:
                aggregated[key] += metrics.get(key, 0)
        
        return jsonify(aggregated)
```

## ⚠️ РИСКИ И MITIGATION

### Риск 1: Регрессия существующей функциональности

**Вероятность:** Средняя  
**Влияние:** Высокое

**Описание:**
Новые детекторы (promised_search, cascade_incomplete) могут вызвать:
- Ложные срабатывания (блокировка корректных запросов)
- Зацикливания (модель не может "пройти" детектор даже после nudge)
- Увеличение количества итераций (2-3 вместо 1)

**Mitigation:**
1. ✅ Тщательное тестирование (см. § План тестирования)
2. ✅ Логирование всех срабатываний детекторов
3. ✅ Soft launch: развернуть на тестовой среде, протестировать 50+ сценариев
4. ✅ Градуальный rollout: сначала для 10% пользователей, мониторинг метрик
5. ✅ Rollback plan: откат к версии до правок в течение 5 минут

### Риск 2: Ложные срабатывания детектора каскада

**Вероятность:** Средняя  
**Влияние:** Среднее

**Описание:**
Регулярные выражения в `_check_cascade_slots` могут не распознать:
- Нестандартные формулировки дат ("на пасху", "в конце лета")
- Нестандартные формулировки состава ("едем семьёй", "я один")

**Mitigation:**
1. ✅ Расширить паттерны регулярных выражений
2. ✅ Добавить fallback: если детектор срабатывает 2 раза подряд → пропустить проверку
3. ✅ Логировать все срабатывания для анализа ложных срабатываний
4. ✅ Итеративное улучшение паттернов на основе реальных данных

### Риск 3: Увеличение количества итераций модели

**Вероятность:** Высокая  
**Влияние:** Среднее (увеличение латентности)

**Описание:**
Детекторы с nudge увеличивают количество итераций:
- Без детекторов: 1-2 итерации в среднем
- С детекторами: 2-4 итерации в среднем
- Увеличение латентности: +1-3 секунды

**Mitigation:**
1. ✅ Оптимизация nudge-сообщений (чёткие, короткие инструкции)
2. ✅ Лимит попыток: максимум 2 nudge, потом "give up"
3. ✅ Мониторинг метрик: если среднее количество итераций > 3 → ревью детекторов
4. ✅ Параллельная оптимизация промпта (лучше предотвратить ошибку, чем исправлять)

### Риск 4: Конфликт детекторов

**Вероятность:** Низкая  
**Влияние:** Высокое

**Описание:**
Несколько детекторов могут сработать одновременно:
- `_is_promised_search` + `_check_cascade_slots` → два nudge подряд
- Модель может "запутаться" в противоречивых инструкциях

**Mitigation:**
1. ✅ Чёткий порядок проверок (каскад → promised_search)
2. ✅ Только один nudge за итерацию
3. ✅ Логирование для отладки конфликтов
4. ✅ Тестирование edge cases
